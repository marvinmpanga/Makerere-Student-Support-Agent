1. TASK OBJECTIVE
-----------------
Implement the get_student_status deterministic tool — a read-only function 
that retrieves a student's academic status, enrollment information, and 
financial hold status. The tool must be schema-validated, exposed via HTTP 
API, and thoroughly tested. It is "deterministic" because for the same 
input it always returns the same output (no LLM involvement, no randomness).


2. WHAT WAS DELIVERED
---------------------

2.1 Pydantic Request/Response Schemas
  File: src/schemas/tools.py

  GetStudentStatusRequest:
    - student_id (str, required): The unique identifier for the student 
      (e.g., student registration number like "123456").

  GetStudentStatusResponse:
    - student_id (str, required): Echo of the input student ID.
    - status (str, required): The current academic status. Values include:
        "Enrolled"  — Active student in good standing
        "Suspended" — Student suspended (usually due to fees or misconduct)
        "Graduated" — Student has completed their program
        "Unknown"   — Student ID not found in the system
    - enrolled_program (str, optional): The degree program name (e.g., 
      "Bachelor of Science in Software Engineering"). Null if not enrolled.
    - financial_hold (bool, default=False): Whether the student has an 
      outstanding financial obligation preventing registration, graduation, 
      or accessing certain services.
    - message (str, optional): A human-readable explanation of the student's 
      current situation (e.g., "Student has pending tuition fees from the 
      previous semester.").


2.2 Core Tool Function
  File: src/core/tools.py — function get_student_status()

  The function uses a MOCK_STUDENT_DB dictionary to simulate a university 
  student records database. In production, this would be replaced with a

  Mock Database Contents:

3. HOW IT WORKS (End-to-End Flow)
----------------------------------

  1. Student (or agent orchestrator) sends a POST request to 
     /api/v1/tools/student-status with a JSON body containing student_id.

  2. FastAPI automatically validates the request body against 
     GetStudentStatusRequest. If validation fails (missing field, wrong 
     type), FastAPI returns HTTP 422 with detailed error messages.

  3. The validated request is passed to get_student_status() in 
     src/core/tools.py.

  4. The function looks up the student_id in MOCK_STUDENT_DB.
     - If found: constructs a GetStudentStatusResponse with the student's 
       actual data.
     - If not found: constructs a response with status="Unknown" and a 
       helpful message.

  5. FastAPI serializes the Pydantic response model to JSON and returns 
     it with HTTP 200.

  6. The agent orchestrator (or calling code) receives the structured 
     response and can use it to inform the LLM's next reasoning step.

  WHY IT IS "DETERMINISTIC":
  - The function contains NO randomness, NO LLM calls, NO external API 
    calls, and NO side effects.
  - For the same student_id input, it will ALWAYS return the exact same 
    output, every time, with zero latency variation.
  - This is a critical architectural decision: deterministic tools are 
    the ONLY way the AI agent can access student data. The AI never 
    queries the database directly.

7. SECURITY CONSIDERATIONS
----------------------------
  - The tool is READ-ONLY. It cannot modify student records.
  - In production, the student_id in the request MUST be validated against 
    the authenticated student's ID to prevent one student from looking up 
    another student's records. This RBAC check is designed in the 
    architecture (component-interfaces.md, Boundary 3) but not yet 
    implemented in code.
  - The mock database contains no real PII. In production, the data source 
    must be encrypted at rest and in transit.
