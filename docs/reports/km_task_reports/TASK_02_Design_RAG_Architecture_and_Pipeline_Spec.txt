3. HOW THE RAG PIPELINE WORKS (End-to-End)
-------------------------------------------

Step 1: INGESTION
  - The KnowledgeIndex.ingest_directory() method reads all .txt and .md 
    files from a specified directory (e.g., data/policies/).
  - Alternatively, ingest_texts() accepts a list of raw text strings.
  - Each document is split into overlapping chunks using a sliding window 
    approach (500 chars, 50 char overlap by default).
  - Each chunk is stored with metadata: source filename, chunk index, 
    and the raw text content.

Step 2: RETRIEVAL
  - When a student asks a question, the pipeline tokenizes the query and 
    each stored chunk into lowercase word sets.
  - A relevance score is computed based on term overlap (number of query 
    terms found in the chunk divided by total query terms).
  - The top-K most relevant chunks are selected (K is configurable).

Step 3: PROMPT CONSTRUCTION
  - build_grounded_prompt() assembles a prompt with:
    • System role instructions ("You are a Makerere student support agent...")
    • The evidence section: each chunk is formatted as 
      "[Source: filename, Chunk N] text content"
    • The student's question
    • An explicit guard: "If the evidence does not contain enough 
      information to answer, say so honestly."

Step 4: ANSWER GENERATION
  - The assembled prompt is sent to the LLM (Gemini 2.5 Flash via the 
    LLM Harness).
  - The model generates a grounded response based solely on the evidence.

Step 5: VALIDATION
  - The answer() method checks if any chunks were retrieved at all.
  - If no relevant chunks are found (evidence sufficiency check fails), 
    the pipeline returns a safe refusal: "I don't have enough information 
    in the approved policy documents to answer that question."
  - This prevents hallucination on topics outside the knowledge base.

6. KNOWN LIMITATIONS & FUTURE WORK
-----------------------------------
  - Retrieval is keyword-based (term overlap), NOT semantic. This means 
    paraphrased questions or synonym-heavy queries may miss relevant chunks 
    even when they exist in the knowledge base.
  - No embedding model is integrated. The spec describes the target state 
    but the actual pipeline does not generate or store vector embeddings.
  - No persistent vector store. All indexed data lives in Python memory 
    and is lost when the server restarts.
  - No re-ranking. Results are returned in raw relevance-score order 
    without a cross-encoder or LLM-based re-ranker.
  - No per-answer trace logging. The spec calls for logging chunk IDs, 
    session IDs, and grounding verdicts, but this is not yet implemented 
    in the pipeline code.
  - These items are explicitly documented in the "What is NOT yet 
    implemented" section of the spec and are earmarked for future sprints.
