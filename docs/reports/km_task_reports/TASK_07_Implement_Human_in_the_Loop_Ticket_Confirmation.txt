1. TASK OBJECTIVE
-----------------
Implement the Human-in-the-Loop (HITL) ticket confirmation system — the 
critical safety gate that prevents the AI agent from submitting support 
tickets without explicit student consent. This task covers:
  a) Schema definitions for confirmation request and response
  b) A pending ticket store to hold drafts between creation and confirmation
  c) A deterministic confirmation function (confirm or cancel)
  d) An API-compatible handler (replacing the old CLI-based input() approach)
  e) An HTTP endpoint for the frontend or agent to call
  f) End-to-end tests covering the full draft → confirm/cancel flow

  TicketConfirmationRequest:

    - student_id (str, required): The student submitting the confirmation.

    - final_status (str, required): "Submitted" if confirmed, "Cancelled"

    - message (str, required): Human-readable result message.
    - audit_event (str, required): A structured audit log event name for 
      downstream logging systems. Values:
        "TICKET_SUBMITTED" — Student confirmed the ticket
        "TICKET_CANCELLED" — Student cancelled the ticket


2.2 Confirmation Function
  File: src/core/tools.py — function confirm_ticket()

  def confirm_ticket(ticket_id: str, confirmed: bool) -> TicketConfirmationResponse:
      """Deterministic confirmation gate — only persists on explicit True."""
      draft = PENDING_TICKETS.pop(ticket_id, None)
      if draft is None:
          raise ValueError(f"No pending ticket found for ID: {ticket_id}")
      if confirmed:
          return TicketConfirmationResponse(
              ticket_id=ticket_id, final_status="Submitted",
              message="Ticket confirmed and submitted.",
              audit_event="TICKET_SUBMITTED"
          )
      return TicketConfirmationResponse(
          ticket_id=ticket_id, final_status="Cancelled",
          message="Ticket cancelled by student.",
          audit_event="TICKET_CANCELLED"
      )

  Key behaviors:
    - Uses PENDING_TICKETS.pop() — this is an ATOMIC consume. Once a ticket 
      is confirmed or cancelled, it is immediately removed from the pending 
      store. It cannot be confirmed twice.
    - Raises ValueError if the ticket_id is not found — this is caught by 
      the API layer and converted to HTTP 404.
    - The function is DETERMINISTIC: same input always produces same output. 
      No LLM involvement, no randomness.


2.3 API-Compatible Handler
  File: src/core/hitl.py (27 lines)

  The original hitl.py used Python's input() function to prompt for 
  confirmation on the command line. This is completely incompatible with 
  a web API — input() blocks the entire server process waiting for stdin.

  The file was refactored to contain two functions:

  confirm_ticket_action() [DEPRECATED]:
    The old CLI handler, preserved for backward compatibility in local 
    testing. Uses print() statements but no input() calls. Returns a 
    simple dict with status and action.

  process_ticket_confirmation() [NEW, API-COMPATIBLE]:
    Accepts a TicketConfirmationRequest Pydantic model.
    Delegates to confirm_ticket() in src/core/tools.py.
    Returns a TicketConfirmationResponse Pydantic model.
    No input() calls — all state comes from the HTTP request body.
    This is the function called by the HTTP endpoint.

3. HOW IT WORKS (End-to-End HITL Flow)
----------------------------------------

  Step 1: DRAFT
    Student (via agent) calls POST /api/v1/tools/draft-ticket
    → draft_support_ticket() creates a draft and stores it in PENDING_TICKETS
    → Response includes ticket_id and student_confirmation_required=True

  Step 2: PRESENT
    The agent presents the draft to the student:
    "I've drafted a Financial support ticket (TKT-A1B2C3D4) about your 
    tuition balance question. Would you like me to submit it?"

  Step 3: DECIDE
    The student either confirms or cancels.

  Step 4a: CONFIRM
    Frontend/agent calls POST /api/v1/hitl/confirm-ticket with confirmed=true
    → confirm_ticket() pops the draft from PENDING_TICKETS
    → Returns final_status="Submitted", audit_event="TICKET_SUBMITTED"
    → In production, this is where the ticket would be written to the 
      university's ticketing database

  Step 4b: CANCEL
    Frontend/agent calls POST /api/v1/hitl/confirm-ticket with confirmed=false
    → confirm_ticket() pops the draft from PENDING_TICKETS
    → Returns final_status="Cancelled", audit_event="TICKET_CANCELLED"
    → The draft is discarded, no ticket enters the system

  Step 5: PREVENT DOUBLE-SUBMIT
    If someone tries to confirm the same ticket_id again:
    → PENDING_TICKETS.pop() returns None (already consumed)
    → ValueError is raised
    → API returns HTTP 404: "No pending ticket found for ID: TKT-A1B2C3D4"


4. WHY HITL IS ARCHITECTURALLY CRITICAL
-----------------------------------------

  The Human-in-the-Loop confirmation gate is one of the system's most 
  important safety features. Here is why:

  a) AI Accountability: The LLM can make mistakes — it might misunderstand 
     the student's issue, miscategorize it, or draft a ticket for the wrong 
     problem. The HITL gate gives the student a chance to catch and correct 
     these errors before they enter the university's support system.

  b) Irreversibility: Once a support ticket is submitted, it triggers 
     real-world workflows — staff assignment, SLA timers, email 
     notifications, priority queuing. These are difficult or impossible 
     to undo. The HITL gate ensures the student explicitly consents before 
     triggering these workflows.

  c) Regulatory Compliance: In an educational institution, AI-generated 
     actions on behalf of students may have policy or legal implications. 
     The HITL gate provides an auditable record that the student approved 
     the action (via the audit_event field).

  d) Prompt Injection Defense: Without HITL, a prompt injection attack 
     could trick the AI into submitting tickets on behalf of students 
     without their knowledge. The HITL gate breaks this attack vector by 
     requiring an explicit out-of-band confirmation.

  e) System Prompt Alignment: The system prompt (prompts/system_prompt_v1.txt) 
     explicitly states: "NEVER take irreversible actions without student 
     confirmation." The HITL API is the code-level enforcement of this rule.

8. KNOWN LIMITATIONS & FUTURE WORK
-----------------------------------
  - In-memory pending store: PENDING_TICKETS is a Python dict in memory. 
    If the server restarts, all pending drafts are lost. For production, 
    use Redis or a database table with TTL.
  - No timeout on pending tickets: A draft can sit in PENDING_TICKETS 
    indefinitely. In production, add a TTL (e.g., 15 minutes) after which 
    unconfirmed drafts are automatically expired.
  - No student_id verification: The confirm-ticket endpoint accepts any 
    student_id without checking that it matches the student who created 
    the draft. In production, cross-check against the session's 
    authenticated student.
  - No edit capability: The student can only confirm or cancel. In a full 
    implementation, the student should also be able to EDIT the draft 
    (change category, update description) before confirming.
