3. WHAT WAS FIXED DURING THIS TASK
------------------------------------

3.1 Bug Fix: CancelAction Missing Terminal Arrow
  BEFORE: The CancelAction state inside the Act composite state had NO 
  outbound transition. In Mermaid stateDiagram-v2, this creates a dead-end 
  state — the diagram is technically broken because the state machine can 
  enter CancelAction but can never leave it.

  AFTER: Added the transition:
    CancelAction --> [*]
  
  This correctly terminates the Act state when a user cancels a ticket, 
  allowing the overall state machine to exit cleanly. Without this fix, 
  a cancel action would have left the agent in an undefined hanging state.

3.2 Commitment of MAX_ITERATIONS
  BEFORE: The prose described the iteration limit as "e.g. 5" — leaving it 
  ambiguous whether the actual value was 5, 10, or configurable.

  AFTER: The prose now states explicitly:
    "If the agent enters a loop (Plan → Act → Observe → Plan...) that 
    exceeds MAX_ITERATIONS (5 steps), execution is forcefully halted."

  The value is committed to exactly 5 steps. This is a design decision, not 
  a suggestion.


4. HOW THE EXECUTION GRAPH WORKS
----------------------------------

4.1 The ReAct Pattern
  The agent follows a Plan-Act-Observe cycle borrowed from the ReAct 
  (Reasoning and Acting) paradigm in LLM agent research:

  PLAN: The LLM analyzes the user's query plus session history. It decides 
  whether it can answer directly (→ FinalResponse) or needs external data 
  (→ Act). It also checks for policy violations (→ SafetyRefusal).

  ACT: If a tool call is needed, the system:
    1. Validates the tool call against the Pydantic schema
    2. Executes the deterministic Python function
    3. Checks if the tool requires human approval
    4. If yes (e.g., draft_support_ticket), enters the HITL gate
    5. The HITL gate blocks until the student confirms or cancels

  OBSERVE: The tool's output is:
    1. Parsed and structured
    2. Saved to the session memory store
    3. Checked against the iteration counter
    4. If iterations < MAX_ITERATIONS, loop back to Plan
    5. If iterations >= MAX_ITERATIONS, exit to ErrorFallback

4.2 Safety Layer
  At the Plan stage, queries are evaluated against safety policies defined 
  in prompts/system_prompt_v1.txt. If a violation is detected (e.g., prompt 
  injection, request to access another student's records, request to perform 
  prohibited actions), the graph immediately redirects to SafetyRefusal, 
  bypassing ALL tool logic. This is a non-negotiable architectural boundary.

4.3 Bounded Execution
  The MAX_ITERATIONS = 5 limit serves as a circuit breaker:
  - In normal operation, a query requires 1-2 iterations (one tool call 
    plus one follow-up if the LLM needs to refine).
  - In adversarial or malformed input scenarios, the agent might enter a 
    loop where it keeps calling tools without converging on an answer.
  - The 5-step limit ensures the agent ALWAYS terminates, even in the worst 
    case, preventing:
      • Infinite token consumption (cost risk)
      • Infinite latency (user experience risk)
      • Denial-of-service via prompt injection (security risk)

4.4 Human-in-the-Loop Gate
  Within the Act state, certain tools are flagged as requiring human approval:
  - draft_support_ticket: Creates a ticket but does NOT persist it.
  - The ticket enters the AwaitConfirmation state.
  - The student must explicitly confirm (→ ReturnResult) or cancel (→ [*]).
  - This ensures the AI can NEVER submit a ticket without human consent.
