1. TASK OBJECTIVE
-----------------
Build a profiling harness that measures end-to-end system latency and 
estimates operational cost for the Makerere Student Support Agent's AI 
workflows. The profiler must:
  a) Execute arbitrary workflow functions and capture latency metrics
  b) Extract token usage (prompt tokens, completion tokens) from responses
  c) Calculate estimated USD cost based on Gemini 2.5 Flash pricing
  d) Generate aggregate reports with averages and totals
  e) Save reports to the evidence directory for audit purposes
  f) Support both mock workflows (for testing) and real LLM/RAG workflows 
     (for production profiling)
  g) Include proper pytest test functions

2.1 SystemProfiler Class
  File: tests/profiling.py (167 lines)

  The SystemProfiler class is a reusable profiling engine:

  Constructor:
    - self.runs = []: Accumulates all profiling run results.

  Method: profile_workflow(name: str, workflow_fn: Callable) -> Dict
    Executes a workflow function, extracts metrics, and records results.
    
    Process:
      1. Calls workflow_fn() — any callable that returns either:
         - A dict with keys: latency_ms, prompt_tokens, completion_tokens
         - An object with attributes: latency_ms, prompt_tokens, completion_tokens 
           (e.g., LLMExecuteResponse)
      2. Extracts latency_ms, prompt_tokens, completion_tokens from the result
      3. Calculates estimated cost using the formula:
         cost = (prompt_tokens / 1,000,000 * COST_PER_1M_PROMPT_TOKENS)
              + (completion_tokens / 1,000,000 * COST_PER_1M_COMPLETION_TOKENS)
      4. Records a run_data dict with all metrics + status
      5. On failure, records error message with status="failed"
      6. Appends to self.runs and returns the run_data

  Method: generate_report(save_path: str) -> str
    Aggregates all runs into a summary report.
    
    Report structure:
      {
        "model_used": "gemini-2.5-flash",
        "total_runs": <int>,
        "successful_runs": <int>,
        "average_latency_ms": <float>,
        "total_estimated_cost_usd": <float>,
        "detailed_runs": [<list of individual run results>]
      }
    
    If save_path is provided, writes the report as formatted JSON to disk.
    Creates parent directories automatically.
    Returns the JSON string regardless of whether it's saved to disk.


2.2 Pricing Constants
  Based on official Gemini 2.5 Flash pricing (as of the implementation date):

  COST_PER_1M_PROMPT_TOKENS  = $0.075  (input tokens)
  COST_PER_1M_COMPLETION_TOKENS = $0.30  (output tokens)
  MODEL_NAME = "gemini-2.5-flash"

  These constants are defined at the module level for easy updating when 
  pricing changes.

  Example cost calculation:
    A typical query using 1,500 prompt tokens and 250 completion tokens:
    Cost = (1500 / 1,000,000 * 0.075) + (250 / 1,000,000 * 0.30)
         = 0.0001125 + 0.000075
         = $0.0001875 per query
    
    At 1,000 queries/day: $0.1875/day ≈ $5.63/month
    At 10,000 queries/day: $1.875/day ≈ $56.25/month

3. HOW IT WORKS (Profiling Session Flow)
------------------------------------------

  1. INSTANTIATE: Create a SystemProfiler() instance.

  2. PROFILE: For each workflow to measure, call:
     profiler.profile_workflow("Workflow Name", workflow_function)
     
     This:
       a) Invokes the workflow function
       b) Extracts metrics from the return value
       c) Calculates cost based on token counts
       d) Records everything in self.runs

  3. REPORT: Call profiler.generate_report() to:
       a) Filter successful runs
       b) Compute average latency across all successful runs
       c) Sum total estimated cost across all successful runs
       d) Write to evidence/profiling_report.json
       e) Return the JSON string

  4. ANALYZE: Open the JSON report to understand:
       - Which workflows are fastest/slowest
       - Which workflows use the most tokens (and therefore cost the most)
       - Whether the average latency meets the user experience target
       - What the projected monthly cost would be at scale


4. COST MODEL EXPLAINED
-------------------------

  The Gemini 2.5 Flash model charges separately for input and output tokens:

  Input (Prompt) Tokens — $0.075 per million tokens
    These are the tokens in the prompt sent TO the model, including:
    - System instructions
    - Conversation history (from the memory store)
    - Retrieved RAG evidence chunks
    - The student's current question
    
    For the Makerere agent, a typical prompt contains:
    - ~200 tokens for system instructions
    - ~500 tokens for history (2-3 turns)
    - ~500 tokens for RAG evidence (2-3 chunks)
    - ~50 tokens for the student's question
    Total: ~1,250 prompt tokens per query

  Output (Completion) Tokens — $0.30 per million tokens
    These are the tokens in the response FROM the model, including:
    - The agent's answer text
    - Any structured output (JSON tool calls)
    
    For the Makerere agent, a typical response contains:
    - ~150-300 tokens for a policy explanation
    Total: ~200 completion tokens per query

  Projected Monthly Costs:
    Low usage  (100 queries/day):  ~$0.019/day  → ~$0.57/month
    Medium use (1,000 queries/day): ~$0.188/day  → ~$5.63/month
    High usage (10,000 queries/day): ~$1.875/day → ~$56.25/month

  These projections assume Gemini 2.5 Flash pricing remains stable. The 
  profiler's constants should be updated if pricing changes.

8. KNOWN LIMITATIONS & FUTURE WORK
-----------------------------------
  - The profiler does not measure wall-clock time independently — it relies 
    on the workflow function to report its own latency. A future version 
    should wrap the call in time.perf_counter() to capture true E2E latency 
    including network overhead.
  - The real_rag_workflow() currently uses mock metrics because the RAG 
    pipeline doesn't report token counts. When the RAG pipeline is upgraded 
    with an embedding model and LLM integration, the profiler should call 
    it directly.
  - No p50/p95/p99 latency percentiles. The current report only shows 
    average latency. For production monitoring, percentile breakdowns 
    are essential.
  - No dashboard or visualization. The report is a flat JSON file. A 
    future version could generate charts or integrate with Grafana/Prometheus.
  - Pricing constants are hardcoded. They should be loaded from a config 
    file or environment variable to allow easy updates without code changes.
